# Comprehensive Codebase Audit Report: Traveloop

## 1. Critical Runtime Errors & Bugs

### 1.1 CommonJS `require` in ESM Module
**Location:** `apps/api/src/repositories/itinerary.repository.ts` (Line 56)
**Issue:** The project uses `"type": "module"` in `package.json`, but `reorderStops` uses `require("../db/index.js")`. This will throw a `ReferenceError: require is not defined` at runtime when trying to reorder stops.
**Impact:** Drag-and-drop reordering of stops will completely fail.

### 1.2 N+1 Query Problem in Public Trip Data
**Location:** `apps/api/src/repositories/public.repository.ts` (`getPublicTripData`)
**Issue:** The code fetches all stops for a trip, then uses a `.map` to iterate over them and executes a separate database query for each stop's activities (`.where(eq(stopActivities.stopId, stop.id)).all()`).
**Impact:** Severe performance degradation when loading public itineraries with many stops.

### 1.3 Catastrophic Performance in City Search
**Location:** `apps/api/src/controllers/explore.controller.ts` (`searchCities`)
**Issue:** The endpoint fetches *all* cities from the database into memory using `.all()`, then applies JavaScript `.filter()` and `.slice()`.
**Impact:** As the `cities` table grows, this endpoint will consume massive amounts of memory and CPU, eventually causing Out Of Memory (OOM) crashes. It should use SQL `LIKE` and `LIMIT`.

### 1.4 Sequential Awaits (Missing Promise.all)
**Location:** `apps/api/src/services/packing.service.ts` (`resetItems`)
**Issue:** The code iterates and updates packing items sequentially. 
**Impact:** Extremely slow for trips with large packing lists. Needs bulk update or `Promise.all`.

## 2. Security Vulnerabilities

### 2.1 Hardcoded/Weak Default Secrets
**Location:** `apps/api/.env.example` & `apps/api/src/config/env.ts`
**Issue:** `JWT_SECRET` defaults to `"super-secret-dev-key-change-me"`. If this fallback is used in production (due to missing environment variable), the entire authentication system is compromised.

### 2.2 Lack of Input Validation on specific routes
**Location:** `apps/api/src/routes/auth.routes.ts` vs Controller
**Issue:** While `signup` and `login` have validation middleware, protected routes (like `updateProfile`) and nested routes might rely solely on controller-level checks or missing Zod schemas. Need a uniform validation middleware application.

### 2.3 Permissive CORS Configuration
**Location:** `apps/api/src/server.ts`
**Issue:** CORS origin might be overly permissive depending on `.env`. In development, it allows `localhost:5173`. Needs strict production validation.

### 2.4 Rate Limiting is Too Broad
**Location:** `apps/api/src/middleware/rateLimiter.ts`
**Issue:** The rate limiter is applied globally to auth routes but may block legitimate users if they share an IP (NAT). More granular limits per user/endpoint are recommended.

## 3. Architecture & Design Flaws

### 3.1 Dual Source of Truth for Database Schema
**Location:** `apps/api/src/db/schema.ts` vs `apps/api/src/db/migrate.ts`
**Issue:** `migrate.ts` uses raw SQL strings (`CREATE TABLE...`) to initialize the database, while `schema.ts` defines the Drizzle ORM schema. If one changes without the other, it will lead to silent failures or ORM crashes. Migrations should be generated by `drizzle-kit` and run via Drizzle's migration runner, not raw SQL strings in code.

### 3.2 Lack of DTOs (Data Transfer Objects)
**Location:** Entire API
**Issue:** Database row types (`inferSelect`) are returned directly to the frontend. This couples the database schema tightly to the API contract and risks leaking sensitive fields (e.g., deletedAt, password hashes if accidentally included).

### 3.3 Repetitive Error Handling
**Location:** All Controllers
**Issue:** Every controller method uses a massive `try/catch` block calling a generic `handleError` function.
**Improvement:** Use an Express async wrapper (`express-async-handler`) and a global error handling middleware to catch thrown exceptions (like `NotFoundError`, `ValidationError`).

### 3.4 Unused SQL Defaults
**Location:** `apps/api/src/db/schema.ts`
**Issue:** Functions like `uuidDefault` and `nowDefault` are declared but their usage is inconsistent or they represent dead code, leading to confusion.

## 4. Frontend & React Specific Issues

### 4.1 Missing Error Boundaries
**Location:** `apps/web/src/App.tsx`
**Issue:** There are no React Error Boundaries. A component crash will unmount the entire application and show a blank white screen.

### 4.2 Exhaustive-Deps ESLint Suppression
**Location:** `apps/web/src/App.tsx` (Line 31)
**Issue:** `// eslint-disable-line react-hooks/exhaustive-deps` used on `AuthInit`. This can lead to stale closures or missing re-renders if dependencies change.

### 4.3 JWT Interceptor Race Conditions
**Location:** `apps/web/src/lib/api.ts`
**Issue:** The token refresh logic uses `pendingQueue` and `isRefreshing` lock. This handles concurrent requests in a *single tab*, but if the user has multiple tabs open, they might trigger multiple simultaneous refresh requests, causing token invalidation (refresh token reuse) and logging the user out.

### 4.4 Hardcoded API URLs
**Location:** `apps/web/src/lib/api.ts` & `public.api.ts`
**Issue:** `http://localhost:4000/api/v1` is used as a fallback. While it uses `import.meta.env.VITE_API_URL`, the hardcoded fallback can accidentally be used in a production build if the env var is misconfigured.

---

## 5. Potential State & Logic Bugs

### 5.1 Date Math Edge Cases
**Location:** `apps/api/src/services/itinerary.service.ts` (`getBudgetSummary`)
**Issue:** Calculates days by subtracting timestamps (`(end - start) / 86400000`). This ignores Daylight Saving Time (DST) transitions, which can result in fractional days (e.g., 4.95 days), throwing off budget calculations.

### 5.2 SQLite Boolean Discrepancy
**Location:** `apps/web/src/lib/packing-notes.api.ts`
**Issue:** The frontend interface defines `isPacked: number; // 0 | 1 (SQLite boolean)`, but uses it as a boolean in some hooks and components (`toggle: (tripId: string, itemId: string, isPacked: boolean)`). Coercion issues may arise if not strictly handled.

---

## Conclusion
This audit reveals a highly functional prototype with typical "hackathon" technical debt. The most urgent issues to fix are the **CommonJS require in ESM** (which breaks app functionality), the **N+1 query in public itineraries**, and the **OOM risk in city search**. Architectural improvements like Drizzle migrations and a global error handler should be implemented before a production release.
